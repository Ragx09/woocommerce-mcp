FINDING F2 — No egress NetworkPolicy default-deny           Severity: Medium
--------------------------------------------------------------------------------
Target: namespaces store + platform (all pods lacking an explicit egress policy)
Steps to reproduce (from the same rogue pods, before deletion):
  store:    curl -m6 https://1.1.1.1/   -> exit=0 connect=0.009413s  (SUCCESS)
  platform: curl -m6 https://1.1.1.1/   -> exit=0 connect=0.016981s  (SUCCESS)
Config: only `default-deny-ingress` exists (policyTypes: ['Ingress']). Egress is
NOT default-denied. Pods woo-mcp, everything-mcp and dashboard DO carry an
Egress policyType (woo-mcp restricted to wordpress:8080 + DNS; everything-mcp
and dashboard have an empty egress = deny-all). But wordpress, mariadb, postgres
and gateway have NO egress restriction and can open connections to any host.
Expected vs actual: a compromised pod should not be able to open arbitrary
outbound connections (C2 / data exfiltration); actual — a pod in either
namespace reached the public internet on :443. Most concerning is the WordPress
pod (large PHP attack surface, internet-reachable via ingress): on RCE it could
freely exfiltrate the WooCommerce DB or beacon out. The MCP servers that matter
most (woo-mcp) are already capped, which limits impact.
Suggested fix: add a per-namespace `default-deny-egress` policy, then explicit
allow rules for DNS (kube-dns :53) plus each workload's required egress
(wordpress->mariadb:3306, gateway->woo-mcp/everything-mcp/postgres and its
external MCP upstreams). Keep the existing woo-mcp/everything-mcp/dashboard
egress rules.
